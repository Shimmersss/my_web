## 1. 产品目标与首版边界

### 1.1 新定位

产品名沿用“月下会客厅”，入口副标题改为“关系探索报告”。推荐主文案：

> 抽三张牌，读懂你靠近爱情的方式。

用户得到的不是身价或婚恋胜率，而是一份有审美、有个人关联、可用于交流的关系说明书。人格类型是熟悉的入口，塔罗是叙事与互动仪式，真正留住用户的内容是具体情境中的矛盾、需求和下一步行动。

成功体验：用户能指出至少两段与自己的回答对应的内容，能保存一张喜欢的卡片，能带走一条可实际使用的话术。

### 1.2 首版必须做

- 新建默认进入关系探索版本，历史定位报告继续按旧版本完整阅读。
- 支持自选四字母人格、原创轻量人格倾向问卷、跳过人格三条路径。
- 固定五个关系偏好主题；全部依靠用户回答，不从收入、年龄、性别推断。
- 三张原创塔罗牌的选择、揭示、持久化及报告联动。
- 六个独立报告章节；任何章节切换都不重复插入总览。
- 真实生成、轮询、失败补偿、内测一次资格、历史列表及删除。
- 本地下载一张专属分享卡，明确控制可分享信息。
- 桌面、390px、320px和 Android 受影响操作验证。

### 1.3 不纳入首版

每日抽牌、连续签到奖励、星座/八字/出生时间命盘、双人合盘、真人撮合、公开报告链接、付费重复洗牌、人格匹配排行榜、社区、订阅、Push 通知、整份 PDF 导出、新供应商接入。

不要把“不追求科学测量”解释成可以伪造验证数据或确定性预言。内容可以诗意、象征性，但不能声称算出对方真实想法、出轨事实、结婚日期、疾病或命定对象。产品只需在入口/牌阵附近用一句克制说明：“人格与牌面提供一种观察关系的视角。”

## 3. 用户流程与交互状态

主路径：进入 → 开始探索 → 关系情境 → 人格路径 → 关系偏好 → 可选生活底稿/伴侣偏好 → 抽三张牌 → 核对费用 → 提交 → 进度 → 报告 → 保存卡片。

默认采用分步骤表单，顶部呈现“第几步/共几步”和可返回的步骤按钮。每一步保留已填值；返回不触发收费或重新抽牌。用户离开后如存在服务端生成任务，返回仍进入原任务状态。

| 状态 | 页面与操作 |
| --- | --- |
| 访客 | 能看介绍；沿用登录/内测兑换入口，提交和抽牌前要求有效身份 |
| 普通登录用户 | 显示当前费用和余额，能够开始新探索 |
| 内测未使用 | 显示一次免费探索，按现有规则允许可选画像 |
| 内测已完成 | 直接访问已有结果，不显示可重复生成承诺 |
| 校验缺项 | 弹窗列出缺项，返回后聚焦首项；保留原输入 |
| 生成中 | 进度/阶段文案、可以离开提示；禁用重复提交 |
| 网络中断 | 使用原串行轮询/退避，不把断网显示为生成失败 |
| 失败待补偿 | 显示处理中，不提前写“已退款” |
| 补偿完成 | 显示可重试，余额/内测资格按真实响应刷新 |
| 过期/删除 | 明确说明，提供返回入口；图片和分享卡入口同步失效 |

输入草稿首版保存在组件状态；不把问卷和精确财务输入写入 localStorage。重载未提交表单可提示需要重新填写。已提交任务用 SQL 快照恢复，不能依赖浏览器缓存。

### 4.2 人格路径和原创16题（保留候选，不作为已选定题库）

本节题目是此前为产品拟写的原创草案，并非从已下载数据库提取。先按第19节审查中文28题候选的来源与计分，再决定最终catalogue。不得把本节题目标为IPIP或官方MBTI。若采用28题，下文16题数量、p01…p16、[-2,2]计算与验收样本须整体替换为经审查的28题合同，不能混用。若来源无法确认，记录原因并采用明确标注本站原创的本节方案，不冒充已验证量表。

四组维度，每组4题。每题同一5档回答：非常偏左=-2、偏左=-1、都可能=0、偏右=1、非常偏右=2。题目左右两端的文字如下。页面每次只呈现少量题，标签完整，不能只画无文字圆点。

自填类型输出 `source=selfReported`，不伪造答题证据或轴分；问卷路径输出 `source=questionnaire`、版本和各轴结果；跳过输出 `source=skipped`，不显示“未知人格有缺陷”。关系五题仍足以生成报告。

## 5. 塔罗规则与持久化设计

### 5.1 首版规则

使用22张大阿尔卡那的原创视觉版本，仅正位；每份报告三张不重复，固定顺序：此刻的你 / 关系中的暗线 / 下一步。去掉恐吓式解释，不做吉凶分数，不显示命运置信度。

牌组 ID 固定为 `major-00` 至 `major-21`，名称依次为：愚者、魔术师、女祭司、皇后、皇帝、教皇、恋人、战车、力量、隐士、命运之轮、正义、倒吊人、死神、节制、恶魔、高塔、星星、月亮、太阳、审判、世界。

固定象征词示例：死神=结束与更新；恶魔=牵引与依赖；高塔=旧结构松动；月亮=不确定与想象。保留牌名和意象，通过温和而明确的解释呈现，不改名掩盖牌义，也不写“会遭遇灾难”。这些短词不是独立来源：实际知识库以第19节的Tarotoo固定版本为结构化起点，并逐牌核对Waite历史文本；保存原文、中文编辑及来源映射。

### 5.2 抽牌体验

用户点击三张背面卡，逐张揭示；不要求拖拽。移动端三张缩略卡完整在屏内，点击后可显示单张详情。翻牌动画200–450ms，减少动态效果偏好下直接切换；不闪烁、不自动播放音效、不强制等待。

牌阵由服务器随机生成并固化，浏览器动画不决定牌序。抽牌不扣积分；正式提交才走现有收费。页面刷新/网络重试恢复同一未过期牌阵，模型重试和生成失败重试不重新抽牌。

### 5.3 建议新增牌阵接口与表

建议新增 POST `/api/matchmaking/tarot-draws` 和 GET `/api/matchmaking/tarot-draws/current`。前者沿用身份、CSRF和现有节目权限；对同一用户复用未消费且24小时内的牌阵，已消费后只有可新建报告的用户才可新抽。无需开放任意ID查询接口。

建议新增 `matchmaking_tarot_draws`：id UUID主键、user_id外键、deck_version、cards_json、created_at、expires_at、consumed_task_id可空、consumed_report_id可空。用户级并发锁必须与当前创建流程协调；同用户并发抽牌只获得一个有效牌阵。可使用独立表的一用户当前行约束/事务内锁定用户行实现，不能仅凭前端按钮禁用。

服务器使用 SecureRandom 做无放回抽样，保存 cardId 与 slot；数据来自白名单牌组。禁止接受客户端指定牌面、方向、权重或任意asset URL。提交只接收 drawId，并校验归属、有效期和消费关系。

牌阵消费与任务创建/扣费在同一事务。任务失败补偿成功后解除消费，保留原三牌并延长有效期24小时供重试；补偿未完成不开放新生成。成功时把牌阵快照写入报告，随后清理临时牌阵不影响报告展示。删除报告、删除全部资料、到期清理必须包含关联牌阵；待补偿任务引用的牌阵不清理。

不引入额外后台线程；清理复用现有计划任务。抽牌接口加有界频率限制，不能通过大量创建消耗库空间。24小时是未提交牌阵有效期，不改变报告原30天期限。

| 亲密关系说明书 | 五个主题，每项“偏好/容易误解/一句表达” | 每项100–160 |
| 反复出现的关系剧本 | 恰好3条：触发→反应→误会→替代方式 | 每条120–200 |
| 你会心动的人 | 吸引你的特质、长期舒服的特质、磨合点 | 每项100–180 |
| 下一次靠近 | 恰好3组沟通情境及话术、1个小行动 | 每组70–130，行动60–120 |
| 现实生活底稿 | 用户自愿信息、确定性账本、缺项说明 | 非模型为主 |

总生成正文目标1800–3000字；上限3600字。输入少时允许更短，不能为了字数编造生活经历。三牌解释须各指向至少一个实际回答或用户自述；人格跳过时用关系题支撑。

称号采用固定可维护候选池，首版12个：温柔的远行者、慢热的守灯人、热烈的理想主义者、清醒的浪漫主义者、安静的同行者、坦率的探索者、细腻的倾听者、自由的共创者、坚定的照顾者、好奇的靠近者、从容的观察者、真诚的筑梦者。模型选一个并解释，不做固定类型→固定称号一对一表。

每条解释区分用户事实和可能性。不得写出用户未提供的创伤史、前任行为、家庭冲突或心理疾病。不得把人格作为对某人的价值判断或现实筛选资格。

示例（仅示例，不写死到所有报告）：

> 你愿意主动靠近，但不一定喜欢关系一直没有说法。你选择了“较早说清期待”，这可能意味着，轻松的互动和明确的回应对你同样重要。下次可以试着说：“我喜欢现在的相处，也想知道你希望我们以怎样的节奏继续。”

合格内容必须包含可追溯的输入证据、合理张力和具体行动。连续出现“你很特别/值得被爱/宇宙会安排”但没有实际关联视为内容质量不合格。

## 7. 数据合同与版本策略

### 7.1 新建请求（结构示意）

```json
{
  "reportVersion": "relationship-exploration-v1",
  "questionnaireVersion": "relationship-questions-v1",
  "relationshipStage": "single",
  "explorationIntent": "understandSelf",
  "personalityMode": "selfReported",
  "declaredType": "ENFP",
  "relationshipAnswers": {"r01": 1, "r02": -1, "r03": 0, "r04": 2, "r05": -1},
  "personalNote": "",
  "drawId": "<server-issued-uuid>",
  "includePartnerImage": false,
  "partnerPreferences": {},
  "lifeContext": {}

```

16题模式接收 `personalityAnswers` p01…p16 的整数；所有数字必须在[-2,2]且为整数。非法mode/type/question ID、重复/缺失必要题、超长字段、对象变数组均返回可理解的400错误，并且不得先扣费。

未知 reportVersion 明确拒绝；请求未带版本时按旧协议处理。新版入口必须显式发送新版本。开关关闭只禁止新版本创建，不禁止读取已有新版报告。

### 7.2 保存的报告结构

```text
id, reportVersion, createdAt, expiresAt
questionnaireVersion, contentVersion, deckVersion
profile: 对外可读的安全资料（不含精确财务输入）
personality:
  source, declaredType?, tendencyCode?, axes?, explanationSource
relationshipPreferences:
  [{id, answerValue, tendencyLabel} × 5]
tarot:
  drawId, drawnAt, deckVersion,
  cards: [{slot, cardId, name, orientation:"upright"} × 3]
narrative:
  identity: {titleId, headline, introduction}
  tarotReadings: [{slot, cardId, interpretation, evidenceIds} × 3]
  relationshipManual: [{dimensionId, preference, misunderstanding, expression, evidenceIds} × 5]
  recurringPatterns: [{trigger, reaction, misunderstanding, alternative, evidenceIds} × 3]
  attraction: {spark, sustainable, friction, evidenceIds}
  nextSteps: {scripts:[{scenario, words, explanation} × 3], experiment}
lifeLedger?: 有输入时的确定性数据；缺失为null
partnerImage?: 沿用现有存储格式和体积约束
```

evidenceIds仅服务端合同和调试使用，匹配 pXX/rXX/用户明确字段白名单；界面不显示实现编号。模型不输出人格分数、牌序或画像asset URL。服务端将确定性结果和模型叙事组装后落库。

不要为了让新报告兼容旧组件伪造 `scores.total=0`。新版SQL `total_score/level` 均为NULL；列表返回 `reportVersion`、可空 `title`、可空 `personalityLabel`，旧报告分数仍保留。确认当前摘要查询和排序没有对NULL强制转换或数值排名依赖。

`source_version` 当前用于数据来源，不能直接覆盖为人格版本：明确保留旧语义；新版可使用固定内容来源标记并在报告JSON独立保存所有版本字段。若必须加摘要列，使用可空新增列，旧数据不回填虚构值。

## 8. 后端实现步骤与事务边界

建议新增：`RelationshipQuestionnaire`（catalogue/校验）、`RelationshipPersonality`（确定性计算）、`TarotDeck`（22牌）、`MatchmakingTarotService`（抽牌与归属）、`RelationshipReportAgent`（新模型合同）。名称可按现有命名调整；不要把整个Service全量重写。

1. 将当前生成分为旧版与新版的内容准备、模型调用、报告组装分支；队列接纳、SQL快照、扣费、补偿和最终保存仍走同一套机制。
2. 创建前完成输入版本校验、牌阵归属、额度、内测和并发校验。
3. 同一事务：扣费/内测占用 + SQL任务 + 牌阵消费。提交后才放入worker。
4. SQL任务request保存新版输入、牌阵固定结果、版本；终态仍按当前规则清除输入副本。
5. 生成阶段复用现有stage key：`scoring`在新版页面显示“整理关系线索”，`writing`显示“写下你的关系解读”；不改共享状态语义。
6. 模型只收到脱敏结构化输入、确定性倾向和三牌象征词，不提供SQL、账户密钥、出生隐私或无关用户信息。
7. 保存事务内写问卷、报告、内测完成、任务完成、牌阵关联。提交完成后才更新内存done状态。
8. 失败补偿沿用 `credit_refund_claims` 及现有对账；牌阵恢复纳入同一补偿完成边界。
9. 删除/保存使用现有互斥语义，不能让worker重新写回用户已删数据。

不提高单worker并发，不在每份报告创建新线程池。牌图是构建时静态素材，不让每个用户生成22张牌。可选伴侣照片仍按当前Images中档配置计费/退款，不把塔罗插画另算用户费用。

## 9. 前端与视觉实现规格

建议按职责拆为：RelationshipQuestionnaire、PersonalityStep、RelationshipPreferencesStep、TarotDrawStep、RelationshipReportView、RelationshipShareCard。旧ReportView仅承担获取/版本分派或保留旧渲染器。避免复制账户逻辑、轮询器和费用计算。

报告导航六项：今夜的你、亲密关系说明书、关系剧本、你会心动的人、下一次靠近、现实底稿。默认今夜的你。移动导航可横向滚动且当前项自动可见；切换后正文起点对齐顶栏以下；键盘可操作，aria-current正确。

总览仅出现在第一章。人格标签不能变成覆盖半屏的大字；人格跳过不留空洞。现实底稿无输入时显示简洁空态，不显示一排0。旧报告的定位总览和全部章节保持原样。

### 9.1 视觉方向

沿用深夜蓝、暖白、古铜金和克制玫瑰色；复用现有token，先取computed style后再微调。标题使用现有本地Noto Serif SC，正文系统中文无衬线。不要全篇加字距或用花体显示长段中文。

长文正文桌面16–18px、手机16px左右、行高1.7–1.9；正文最大行宽约36–42个汉字。卡片以留白、细边和纸感组织，不层层套厚边框。背景遮罩只保证可读性，保留月亮和灯光主体。

### 9.2 素材交付清单

- 22张原创牌面：2:3比例，建议768×1152母图；交付WebP/JPEG适配图，目标单张80–180KB。
- 1张统一牌背；1张三牌舞台背景；1张分享卡背景。现有月夜素材可复用。
- 字体许可与每张图生成来源/提示词/文件映射记录；生产素材不含私人问卷。
- 牌名、序号、正文均由HTML叠加，不要求生图模型画中文。

统一生图提示方向：月夜私人会客厅、古铜金细线、夜蓝与暖纸、柔和油画质感、单一清晰象征主体、统一画框、无文字、无商标、无现成商业牌组图案。逐张改变象征主体；先完成3张代表牌核对风格，再做完整22张，不能把一张拼图粗裁成模糊牌组。

生图工具缺失时先补齐必要环境；若实际需凭据，列出具体缺项。不能用Emoji、空白框或低质量占位牌宣称素材验收完成。AI绘画为静态资源，图表/控件仍用正常组件实现。

性能：入口不预加载22张大图；只加载牌背和必要背景，抽取后加载三张；图片width/height固定、lazy loading、失败替代为清楚的牌名和固定象征文字。生产构建检查单独字体/图片传输，不新增几十MB首屏请求。

## 10. 分享卡与隐私

首版只生成本地图片，不提供公开URL、自动上传或社交平台发送。内容仅含产品名、关系称号、短句、三牌名称/意象。四字母人格默认不展示，用户勾选后才加入。不得加入姓名、账户名、报告ID、输入原文、收入、家庭情况或内测码。

建议用本地canvas绘制分享卡，等待字体和同源素材ready；文字主动测宽换行，不截断关键句。固定1080×1440输出，PNG。预览与实际下载一致；长称号/跳过人格/图片失败都要验收。

桌面浏览器走标准Blob下载；Android若现有桥接不支持Blob/图片保存，不臆造新桥接API：先检查 `android/README.md` 和现有 bridge 能力。在不改变原生壳的首版可使用现有受支持下载链路或明确提供浏览器下载入口；若要求App内直接保存而需桥接扩展，应作为显式子任务完整实现并升APK版本，不能把失败算成功。

生成临时Blob URL在替换/卸载时释放；不将报告全JSON塞进二维码、URL查询参数或图片元数据。分享卡没有传播追踪参数。
