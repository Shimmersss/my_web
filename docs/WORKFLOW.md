# 项目工作流

本文件维护开发到交付的共同步骤。产品概览见 [README](../README.md)，部署见 [DEPLOYMENT](../DEPLOYMENT.md)。仓库根目录为以下命令的默认工作目录。

## 文档职责

| 文档 | 内容 | 更新时机 |
| --- | --- | --- |
| README.md | 项目功能、启动入口、目录导航 | 对外能力或启动方式变化 |
| AGENTS.md（本地） | 长期约束、协作入口 | 每次更新核对；约束/导航变化时修改 |
| docs/WORKFLOW.md | 开发、验证、交付规范 | 流程变化 |
| DEPLOYMENT.md | 发布前置条件、操作顺序、恢复边界 | 部署能力或存储模型变化 |
| MAINTENANCE.md（本地） | 最近验证的生产版本、备份、运维检查 | 上线或运维核验后 |
| WORKLOG.md（本地） | 最近变更及证据索引 | 每次完成更新 |
| docs/plans/ | 当前复杂任务范围与验证计划 | 跨模块/高风险工作 |

本地文档可能因 gitignore 不在新克隆中；共享流程不能依赖只有本机存在的脚本或文件。历史日志、已完成计划、临时路径不构成当前指令。配置默认值查 `.env.local.example` 和 `application.yml`，脚本能力查源码；不要在多份文档复制完整参数表。

## 1. 定义任务

- 阅读用户目标，确认涉及的模块、验收场景、生产操作授权。
- 用 `git status --short` 和 `git branch --show-current` 确定工作区基线；记录已有改动，避免混入或覆盖。
- 小修直接实施；跨模块、数据迁移、计费和任务状态机修改，先在 `docs/plans/` 记录问题、范围、不包含项、兼容性、验证和回滚边界。
- 需要确认时只问尚缺的信息；已经授权的读写操作不重复确认。

## 2. 准备与实施

- 检查 Java 17、Maven、Node/npm；文档生成另需 uv、稳定版 LibreOffice、Poppler、Chromium、字体。以当前脚本要求为准，不跳过依赖。
- 安装 JS 锁定依赖：`npm --prefix backen ci`、`npm --prefix front ci`。
- 本地配置使用根 `.env.local`，然后 `./project.sh start`。用 `./project.sh status` 确认端口和服务；不要假定测试启动会加载生产配置。
- 先定位错误触发条件；修改最小必要范围，保持接口兼容。计费/权限/恢复问题补能够失败的行为测试，而非复写实现。
- 外部模型和收费服务使用受控测试；测试数据与真实数据隔离，临时账号/会话/进程在结束时清理。

## 验证矩阵

| 修改范围 | 必需检查 | 额外验收 |
| --- | --- | --- |
| 纯 Markdown | 链接目标、命令存在性、陈旧/冲突规则、`git diff --check` | 本地归档仍受忽略；无敏感信息进入公共文件 |
| Vue/JS/样式 | `npm --prefix front run build` | 受影响路由、桌面/移动、控制台、权限/空态/错误态 |
| Java 业务 | 定向测试，随后 `mvn -f backen/pom.xml test` | 相关API、错误码、事务与权限 |
| Node PPT/HTML worker | `npm --prefix backen test` | 改渲染时验真实产物、预览、字体与质量报告 |
| SQL/计费/异步任务 | Java测试 + 隔离MySQL集成 | 并发、回滚、重启、退款失败、删除竞态 |
| Android 容器/文件链路 | Android文档中的构建与测试 | 模拟器/真机上传、下载、深链；需要时发布APK |
| 部署流程 | shell语法、发布前完整门禁、恢复方案审查 | 按DEPLOYMENT执行线上验证 |

MySQL专项：在独立本地测试实例提供 `WEB_TEST_MYSQL_URL`、`WEB_TEST_MYSQL_USER`、`WEB_TEST_MYSQL_PASSWORD`，执行 `mvn -f backen/pom.xml -Dtest=MatchmakingMySqlIT test`。测试会创建和删除随机测试库，需要相应权限；不使用生产地址或生产用户。

同一代码与依赖状态下已通过的检查可以复用，记录命令和结果；后续相关改动或失败才重跑。发布脚本仍执行它要求的门禁。没有现成 lint/CI 命令就不要写“lint/CI已通过”。

## 3. 最小审查

- 对照任务范围检查最终 diff，确认未覆盖用户已有修改。
- 检查正常/失败/空态，读写权限、并发与回滚；涉及任务还要看取消、重启和补偿。
- 对照测试结果说明证据边界；本地通过不代表生产配置正确，构建通过不代表视觉正确。
- 复杂页面按职责拆分；不在修复中加入无关架构改造。新发现的独立问题写后续事项。

## 4. 交付与发布

- 无生产授权时停在完成本地验证的可审阅成果；用户要求部署时按DEPLOYMENT执行。
- 记录 release ID、源码基线/dirty状态、备份及兼容性、迁移结果、线上端点/产物/浏览器验证。
- 发布失败先定位在哪一步，再决定继续验证、修复或恢复；不要因末尾统计错误盲目回滚已验证的新服务。
- 最后更新 WORKLOG；长期约束变化更新 AGENTS，生产核验更新 MAINTENANCE。报告必须明确“本地完成”或“已上线验证”。

## 变更记录模板

每次一条，避免把同一历史事实复制到多个入口：

```text
日期 / 标题 / 状态（本地完成、已上线验证、待处理）
问题与范围：
结果与兼容性：
验证：具体命令、结果、未覆盖范围
发布：release / 备份 / 恢复限制（如适用）
后续：独立事项及证据路径
```

根WORKLOG保留近期记录；旧记录完整归档并提供索引和日期。归档不改变旧结论的时间属性，不能把当时“未部署”误当作当前状态。

## 流程能力的实际边界

目前测试和发布入口以本地命令为主；不要宣称已有持续集成平台、自动全库备份、四模块统一任务排空或SQL兼容回滚。现有发布脚本的具体缺口见DEPLOYMENT。未来补齐自动化时，应先添加实现及失败路径验证，再更新这些说明。
